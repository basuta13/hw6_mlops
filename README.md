# Авито: автоматическая пре-модерация нового объявления

Домашнее задание по MLOps: архитектурные схемы ML-системы (BPMN + C4).

**Компания:** Авито.
**Процесс:** решение о публикации нового объявления до того, как оно попадёт в поиск.
**Результат процесса:** объявление либо опубликовано, либо отклонено, и продавец получает причину отказа. Попутно в датасет для следующего обучения модели уходит метка.

---

## 1. Что решает модель

| | |
|---|---|
| **Вход** | Новое объявление: заголовок, описание, категория, цена, до 5 фото; признаки продавца (возраст аккаунта, число прошлых отказов и блокировок, жалобы за 30 дней). |
| **Выход** | `score` — откалиброванная вероятность того, что объявление нарушает правила (0…1); `reason_code` — самый вероятный класс нарушения; `model_version`. |
| **Классы нарушений** | запрещённый товар · контакты в тексте или на фото · признаки мошенничества · неприемлемое фото · неверная категория. |
| **Что нужно бизнесу** | Публиковать честные объявления за секунды, без очереди к модератору; не пускать в поиск нарушения; отправлять людям только спорные случаи, потому что ручная проверка дорогая. |

**Кто получает результат модели.** Напрямую его получает **Оркестратор модерации**: по `score` он выбирает ветку процесса. Через него результат доходит до трёх получателей:
- **Платформа объявлений** получает вердикт: публикует объявление или отклоняет его;
- **продавец** получает уведомление о публикации или причину отказа, она строится из `reason_code`;
- **модератор** получает задание, если `score` попал в серую зону. Свой вердикт он ставит сам, а `score` и `reason_code` видит как подсказку.

### Пороги (заданы мной)

| Условие | Решение |
|---|---|
| `score ≥ 0.92` | автоматически отклонить, причина = `reason_code` |
| `score ≤ 0.15` | автоматически опубликовать |
| `0.15 < score < 0.92` | серая зона → ручная проверка |
| нет ответа модели за 500 мс (таймаут, 5xx, сервис недоступен) | ручная проверка |

Как выбраны пороги: на отложенной выборке точность авто-отклонения должна быть не ниже 98% (честного продавца нельзя отклонять без человека), а доля пропущенных нарушений среди авто-публикаций — не выше 0,5%. Значения 0.92 и 0.15 условные, при каждом выпуске модели их пересчитывают. 500 мс — это SLA шага: продавец должен увидеть «опубликовано» почти сразу.

## 2. Границы работы

**Входит в схемы:**
- одно новое объявление от нажатия «Разместить» до публикации или отказа;
- жёсткие правила перед моделью (стоп-слова, продавец в бан-листе);
- вызов модели, пороги, запасной путь через модератора;
- контрольная выборка авто-решений и запись меток для следующего обучения;
- компоненты ML-сервиса: признаки, выбор версии модели, инференс, ответ;
- на уровне контейнеров — путь, по которому модель попадает в прод: переобучение → реестр → ML-сервис.

**Сознательно за рамками:**
- редактирование уже опубликованного объявления и повторная модерация;
- пост-модерация: что происходит с объявлением после жалобы покупателя. Сюда входят только итоговые метки из жалоб;
- внутренний процесс апелляции продавца и блокировка аккаунтов;
- автоматическое исправление нарушений (например, замазывание контактов на фото);
- индексация в поиске, платное продвижение, оплата размещения;
- мониторинг, алерты, A/B-тесты и внутреннее устройство пайплайна обучения.

## 4. Схема BPMN

![BPMN](diagrams/01-bpmn-moderation.png)

**Легенда BPMN**

| Фигура на схеме | Элемент BPMN |
|---|---|
| рамка с заголовком ( Продавец, Оркестратор …) | дорожка (lane) |
| зелёный круг | стартовое событие |
| красный двойной круг | конечное событие |
| прямоугольник | задача |
| **оранжевый прямоугольник с толстой рамкой (M2)** | **задача, в которой вызывается модель** |
| фиолетовый прямоугольник | задача запасного пути (человек) |
| зелёный прямоугольник | задача обратной связи (метка для обучения) |
| ромб | исключающий шлюз XOR |
| шестиугольник «+» | параллельный шлюз AND |
| сплошная / пунктирная / жирная стрелка | основной поток / запасной путь / путь метки в обучение |

**Ход процесса**
1. Продавец нажимает «Разместить». Платформа сохраняет объявление со статусом «На проверке» (P1) и отправляет событие `item.created` (P2).
2. Оркестратор проверяет жёсткие правила (O1). Если правило нарушено (G1), объявление отклоняется без модели.
3. Иначе Оркестратор запрашивает оценку (O2). ML-сервис собирает признаки (M1) и **вызывает модель (M2)**.
4. **G2:** ответ не пришёл за 500 мс → **запасной путь:** задание в очередь ручной проверки (O3).
5. **G3:** `score` сравнивается с порогами. Высокий — отклонить, низкий — опубликовать, серая зона — **запасной путь** (O3 → H1 → G5).
6. Вердикт, `score` и версия модели записываются (O4). Дальше процесс идёт параллельно (AND):
   - вердикт уходит на платформу (O5 → G8). Там объявление публикуется (P3) или продавцу отправляется причина отказа (P4);
   - **G6** решает, нужна ли метка. Решение модератора всегда становится меткой. Авто-решение становится меткой, если попало в случайные 2%: тогда его перепроверяет модератор (H2). Метка сохраняется в датасет (T1) и уходит в следующее обучение.

### Запасные пути
| Ситуация | Что делает процесс |
|---|---|
| Сработало жёсткое правило (G1) | **правило**: отказ без вызова модели |
| Модель не ответила за 500 мс / ошибка (G2) | **человек**: задание модератору |
| `score` в серой зоне (G3) | **человек**: задание модератору |
| Новая версия модели не загрузилась в сервис | **предыдущая версия модели**: Резолвер версии остаётся на `previous` (видно на схеме Components) |

### Откуда метки и оценка качества
- **Решения модераторов по серой зоне.** Метки качественные, но смещённые: в них попадают только спорные объявления.
- **Контрольная выборка 2% авто-решений.** Даёт несмещённую оценку точности авто-отклонения и доли пропущенных нарушений, то есть именно тех метрик, по которым подбираются пороги.
- **Жалобы покупателей и итоги апелляций** приходят с задержкой. По ним видно, что модель пропустила или отклонила зря.
- **Лог предсказаний** (признаки + `score` + версия) связывается с метками по `item_id`, из этого собирается обучающий датасет.

## 6. C4 — уровень 2: Containers

![C4 Containers](diagrams/03-c4-containers.png)

Шаги 1–9 на стрелках — основной путь одного объявления. Пунктир — запасной путь через человека, жирные линии — данные для переобучения. В каждом контейнере подписано, какие задачи BPMN он выполняет. Путь модели в прод: **Пайплайн переобучения → Реестр моделей → ML-инженер переводит кандидата в production → ML-сервис загружает версию**.

## 7. C4 — уровень 3: Components ML-сервиса

![C4 Components](diagrams/04-c4-components-ml.png)

- **Откуда признаки:** Сборщик признаков читает признаки продавца из Online Feature Store (Redis). Текст и ссылки на фото приходят в запросе, фото скачиваются из Хранилища медиа. Это задача **M1**.
- **Где выбирается версия модели:** Резолвер версии модели держит в памяти `production` и `previous` из реестра MLflow и подставляет веса в блок инференса. Если новая версия не загрузилась, сервис остаётся на `previous`.
- **Где считается ответ:** энкодеры текста и фото → Классификатор нарушений (CatBoost) → Калибровка. Это задача **M2**.
- **Куда уходит результат:** Scoring API возвращает `score`, `reason_code`, `model_version` в Оркестратор, то есть в шлюзы **G2/G3** на BPMN. Копия ответа уходит в лог предсказаний (Kafka).

Остальные контейнеры системы на эту схему не перенесены. Серым показаны только соседи, с которыми ML-сервис обменивается данными, чтобы было видно, откуда приходят входы и куда уходит ответ.

## 9. Допущения

Всё ниже я не могу знать снаружи — это моя реконструкция.

**Регламент и бизнес-правила**
1. Каждое новое объявление проходит пре-модерацию: до вердикта его нет в поиске.
2. Перед моделью стоят жёсткие правила (стоп-слова, бан-лист продавцов). Они срабатывают без модели.
3. Пороги 0.92 / 0.15, SLA 500 мс и контрольная выборка 2% придуманы мной. Внутренний регламент Авито неизвестен.
4. Модератор видит `score` и `reason_code` как подсказку, но решает сам.
5. Решение модератора — окончательное в рамках этого процесса. Апелляция — отдельный процесс.
6. Переобучение раз в неделю; новую версию в production переводит человек (ML-инженер), а не автоматика.

**Модель и данные**
7. Одна мультимодальная модель на все категории: энкодеры текста и фото + CatBoost-голова. 5 классов нарушений — мой упрощённый список.
8. Признаки продавца считаются заранее (раз в 15 минут) и читаются из Redis по `seller_id`. Признаки объявления считаются на лету.
9. Если признака продавца нет (новый аккаунт), подставляется значение по умолчанию. Это само по себе признак риска.
10. Калибровка — изотоническая; `score` — максимальная вероятность среди классов.

**Технологии**
11. Kafka как шина событий, Go для оркестратора, Python/FastAPI + ONNX Runtime для инференса, Redis, PostgreSQL, ClickHouse, S3, MLflow, Airflow, Spark, React — типичный стек для такой задачи. Реальный стек Авито может отличаться.
12. Оркестратор вызывает ML-сервис синхронно по HTTP. Асинхронная обработка возможна, но для схемы я выбрал синхронный вызов, чтобы шаг с моделью было проще прочитать.
13. Хранилище медиа, профиль продавца, сервис жалоб и сервис уведомлений — отдельные системы, не входящие в систему модерации.
